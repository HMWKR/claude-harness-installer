# Remotion vs motiscope — 실측 비교와 라우팅 기준 (2026-10-16)

> 사용자 지시(2026-10-16): "Remotion이랑 motiscope랑 차이를 보며 어떤게 더 나은지 체크를 한 다음 문서를 작성 … 아예 한쪽을 없애는 게 아닌 더 나은 쪽 위주로 진행". 이 문서가 두 도구의 라우팅 정본이고, 라우터(`scripts/uiux-skill-router.sh`)의 "녹화→웹 모션" 블록과 영상 블록이 이 결론을 따른다.

## 한 줄 결론

두 도구는 경쟁 관계가 아니라 **방향이 반대**다. Remotion은 **코드 → 영상**, motiscope는 **영상 → 측정값·웹 코드**다. 그래서 "어느 쪽이 낫냐"는 산출물과 입력으로 갈린다.

| 상황 | 위주로 쓸 도구 | 보조 | 쓰지 않는 쪽과 이유 |
|---|---|---|---|
| 결과물이 **영상 파일**(히어로 무음 루프, 제품 데모, 쇼츠, 소개 영상) | **Remotion** | ffmpeg-skill(후처리·납품 검사) | motiscope — 영상을 만들지 못한다 |
| **참고 녹화**(경쟁사 화면 녹화, mp4·mov·gif)를 보고 **우리 웹에 같은 움직임** | **motiscope**(analyze → 프레임을 직접 보고 수치 교정 → recreate 대신 `animate`·`motion`으로 CSS/JS 구현) | aside repl로 구현 결과의 `getAnimations()` 값 대조 | Remotion — 영상을 분석하지 못하고, 웹 UI 모션을 영상으로 박으면 상호작용·접근성·용량이 나빠진다 |
| 참고 녹화 없이 **웹 UI 모션을 새로** 만들기 | 둘 다 아님 → `animate`·`emil-design-eng`·`motion`(무료 문서) | animation-performance | — |
| 참고 녹화를 보고 **영상으로** 다시 만들기(예: 경쟁사 소개 영상의 리듬을 참고한 우리 데모 영상) | **Remotion**(제작) | **motiscope**(참고 영상의 구간·홀드·시차를 먼저 재서 Remotion 타임라인 숫자로) | — 둘을 이어 쓴다 |
| motiscope의 측정 정확도를 확인하거나 보정 | **Remotion**(이징·시점을 아는 정답 클립 렌더) | motiscope | — 이 문서의 실험 방식 |

## 실측 (같은 조건, 2026-10-16 메인 세션)

**정답 애니메이션**(Remotion 4.0.535 스크래치 프로젝트로 작성): 1280×720·60fps·2초. 청록 상자가 0.2→0.8초에 x 100→1000px, 이징 `cubic-bezier(0.23,1,0.32,1)`(강한 ease-out) 후 정지. 점 3개가 0.9/1.0/1.1초(시차 0.1초)에 0.3초 동안 opacity 0→1 + y 40→0, `cubic-bezier(0.215,0.61,0.355,1)`(ease-out). 점은 **왼쪽→오른쪽** 순.

### Remotion — 코드 → 영상
- 렌더: `npx remotion render` 40.5초(첫 실행, Chrome Headless Shell 포함) → H.264·yuv420p·1280×720·60fps·**120프레임·2.000초**(`remotion ffprobe` 검산).
- 정확도: 프레임 PNG에서 상자 왼쪽 끝 픽셀을 해석값과 대조.

| 프레임 | 시각 | 해석값 x | 렌더 x | 오차 |
|---:|---:|---:|---:|---:|
| 12 | 0.200 | 100.0 | 100 | 0.0 |
| 24 | 0.400 | 889.2 | 890 | 0.8 |
| 30 | 0.500 | 969.4 | 970 | 0.6 |
| 48 | 0.800 | 1000.0 | 1000 | 0.0 |
| 54 | 0.900 | 1000.0 | 1000 | 0.0 |

→ 픽셀 반올림 수준(≤0.8px)으로 정확하다. 프레임 단위 결정적 렌더라 같은 코드는 같은 영상을 낸다.

### motiscope — 영상 → 측정값
- 분석: `motiscope analyze truth.mp4 --preset detailed` **8.6초**, 프레임 10장 + 에너지 곡선 + 구간 표.

| 항목 | 정답 | motiscope 결과 | 판정 |
|---|---|---|---|
| 길이·fps·해상도 | 2.00s·60·1280×720 | 2.00s·60·1280×720 | 맞음 |
| 상자 이동 구간 | 0.20–0.80s | 0.00–0.65s(별도 '정지' 목록엔 0–0.217s 홀드를 잡음) | 시작 0.2s·끝 0.15s 어긋남 — 꼬리의 미세 이동은 임계값 아래로 빠짐 |
| 상자 이징 종류 | ease-out(강함) | **ease-in-out** `0.65,0,0.35,1` | **틀림** — 에너지 곡선 모양(첫 프레임 최대 후 감쇠)은 ease-out인데 분류기가 프리셋을 잘못 고름 |
| 점 구간 | 0.90–1.40s | 0.92–1.28s | 대략 맞음 |
| 점 이징 | ease-out | **linear** | **틀림** — 시차로 겹친 합 곡선(measurement-traps §6) |
| 시차 | 0.1s, 왼→오 | **~474ms, 위→아래**(신뢰도 0.89) | **틀림** |
| 골라 준 프레임 | — | t=1.13s 프레임에서 점 3개가 왼→오 순으로 진해지는 것이 보임 | 모델이 프레임을 보면 시차 방향·순서를 바로 교정할 수 있다 |

→ motiscope의 가치는 **"어디를 봐야 하는지"(구간 경계·홀드·대표 프레임)를 8초 만에 골라 주는 것**이다. 이징 종류·cubic-bezier·시차 숫자는 **그대로 믿으면 안 된다**(이번 실험 3/3 틀림 — README도 '정확한 제어점은 프레임에서 복원 불가'라고 적는다). 결과에는 항상 '프리셋 근사'로 표기하고 프레임을 직접 열어 교정한다.

## 두 도구를 같이 쓰면 더 정교한가 — 실측 (2026-10-16, 사용자 추가 요청)

과제: 위 정답 녹화(`truth.mp4`)를 보고 같은 움직임을 재현한다. 후보는 같은 장면을 매개변수(상자 시작·끝·이징, 점 시작·길이·시차·이징)로 받는 Remotion 컴포지션 `Cand`로 렌더하고, 정답과 프레임 단위로 채점했다(`score.py`: ffmpeg PSNR, 행 270의 상자 왼쪽 끝 픽셀, 점 중심 밝기). 정답끼리 비교하면 오차 0(inf dB·0px·0%)인 것을 먼저 확인했다.

| 방식 | 값을 정한 방법 | PSNR 평균 / 최저 | 상자 최대 오차 | 점 투명도 오차 | 비용 |
|---|---|---:|---:|---:|---|
| A. motiscope 단독 | report 수치 그대로(0–0.65s ease-in-out, 점 linear·시차 474ms) | 26.0 / 20.3 dB | 188px | 22.0% | 분석 8.6초 |
| B. motiscope + 프레임 판독 | 정지 목록의 0.217s 출발, 0.33s 프레임에서 77% 진행 → 강한 ease-out(Quint), 끝을 0.75s로 늘림, 1.13s 프레임의 진함 차이 → 시차 0.1s·왼→오 | 35.7 / 21.5 dB | 107px | 0.12% | 프레임 몇 장 확인 |
| C. B + Remotion 검증 루프 | B 주변 24후보(시작 0.2/0.217 × 끝 0.75/0.8/0.85 × 표준 ease-out 4종 — **정답 이징은 후보에서 뺌**)를 렌더해 정답 녹화와 대조, 오차 최소 선택 | **41.8 / 32.0 dB** | **10px** | 0.12% | 렌더 24회 107초 |

- C의 최적값은 0.2–0.8s·`easeOutQuint(0.22,1,0.36,1)`이다. 구간은 정답과 일치했고, 이징은 표준 프리셋만으로도 10px 안에 들어왔다. 최악 후보(0.217–0.85s·Cubic)는 244px였으니, 그럴듯해 보이는 값 사이에도 차이가 크다.
- 각 도구의 몫: **motiscope = 어디를 볼지**(구간·홀드·대표 프레임), **모델의 프레임 판독 = 무엇이 움직이는지와 이징 종류·시차 방향**, **Remotion = 후보를 결정적으로 렌더해 정답 녹화와 숫자로 비교하는 검증기**. 셋 중 하나를 빼면 A·B 수준으로 떨어진다.
- Remotion의 `Easing.bezier(x1,y1,x2,y2)`는 CSS `cubic-bezier()`와 정의가 같아, 찾은 값이 그대로 CSS·Web Animations로 옮겨진다(웹 결과물은 코드로 만들고 영상으로 박지 않는다).

### 언제 C까지 가나
- **정교함이 중요할 때**(경쟁사 시그니처 모션을 맞춰야 하거나, 고도화 루프의 모션 기준이 L3 이상일 때): A → B → C. 시간이 2~3분 더 들고 매개변수형 재현 컴포지션을 하나 짜야 한다.
- **대략 같은 느낌이면 될 때**: A → B에서 멈춘다. B만으로도 점처럼 단순한 요소는 정답과 거의 같았다.
- A에서 멈추지 않는다. 수치를 그대로 쓰면 이번 실험에서 가장 나빴다.

### 한계
- 이번 정답은 깨끗한 합성 영상이다. 실제 화면 녹화는 압축 잡음·배율·스크롤·배경 변화가 있어 픽셀 추적 채점기를 장면마다 맞춰야 하고, 오차는 이보다 클 것이다 [추정].
- 채점기는 요소 색과 위치를 아는 장면용이다. 복잡한 장면은 PSNR·SSIM 같은 전체 지표나 요소별 마스크가 필요하다.
- Remotion 무료 대상은 개인·직원 3명 이하 영리 조직·비영리·평가 목적이다. 이 보정 루프는 평가 용도로 스크래치에서만 돌리고, 회사 직원 수는 [미확인]이라 영상 산출물 상용 배포는 레지스트리 §5의 라이선스 메모를 따른다.

## 운용 규칙

1. **녹화 → 웹 모션**: `motiscope analyze` → report.md의 구간·홀드만 받아들이고, 이징·시차는 프레임을 열어 직접 판정 → (정교함이 필요하면) Remotion 매개변수 컴포지션으로 후보를 렌더해 원본 녹화와 프레임 대조·후보 탐색 → `animate`(결정 순서)·`emil-design-eng`·무료 `motion` 문서로 CSS/JS 구현(이 저장소 토큰 우선, CSP 때문에 CDN GSAP·인라인 스크립트 산출물은 그대로 쓰지 않음) → aside repl로 구현 결과의 `document.getAnimations()` duration·easing·delay를 읽어 측정 구간과 대조. `motiscope-recreate`의 단일 HTML은 참고용.
2. **영상 산출물**: 라우터 영상 블록(Remotion) 그대로. 참고 영상이 있으면 그 전에 motiscope로 구간·홀드를 재 Remotion 타임라인 숫자의 출발점으로 쓴다.
3. **웹 UI 모션을 영상으로 대체하지 않는다**: 히어로 배경처럼 상호작용이 없고 실시간 렌더 비용이 큰 장면만 Remotion 영상(포스터·감속 모드 정지·두 코덱·용량 예산)으로. 버튼·카드·전환은 코드로.
4. **보정 실험이 필요할 때**: 이 문서처럼 Remotion으로 정답 클립을 만들어 motiscope에 넣는다(스크래치 폴더, 프로젝트에 남기지 않음).
5. 입력 녹화는 사용자가 만든다(Aside는 CDP 차단으로 녹화 불가). 생성형 영상이 필요하면 fal.ai(+Blender 기준 프레임)로 따로 만들고, 이 두 도구는 측정·정리에 쓴다.

## 재현
- 스크래치: `package.json`(remotion·@remotion/cli 4.0.535, react 19.1.0) + `src/Root.tsx`(위 정답 컴포지션 `Truth`) + `remotion.config.ts`(png·yuv420p) + `tsconfig.json`.
- `npx remotion render src/index.ts Truth out/truth.mp4` → `motiscope analyze out/truth.mp4 --preset detailed --out moti-out`.
- 프레임 대조: `npx remotion render … --sequence --frames=12,24,30,48,54 --image-format=png` 후 행 270의 청록 픽셀 왼쪽 끝을 해석값(`cubic-bezier` 이분법)과 비교.
