# Project Quality Loop

사용자 요청: `$ARGUMENTS`

이 스킬은 프로젝트 종류에 맞는 검수 모듈을 자동 선택하고, **발견 → 기준 정의 → 실행 → 증거 수집 → 독립 검수 → 수정 → 재검수 → 품질 게이트**를 수행한다.

## 0. 실행 모드 해석

첫 번째 인자가 아래 값이면 모드로 사용한다. 없거나 불명확하면 `full`로 간주한다.

- `plan`: 조사·분류·계획·완료 조건만 작성한다. 프로젝트 산출물은 수정하지 않는다.
- `audit`: 산출물은 수정하지 않고 검수·증거 수집·보고서 작성만 한다.
- `fix`: 이미 알려진 문제와 재현 가능한 문제를 수정하고 재검수한다.
- `full`: 요구사항 보완, 구현, 종합 검수, 수정, 재검수를 모두 수행한다.
- `release`: 배포하지 않고 출시 가능 여부를 엄격하게 판정한다.

나머지 인자는 목표와 범위다. 범위가 없으면 현재 프로젝트 전체를 대상으로 한다.

## 1. 절대 운영 원칙

1. 저장소와 산출물을 먼저 조사한 뒤 수정한다.
2. 저장소에서 확인 가능한 내용을 사용자에게 다시 묻지 않는다.
3. 되돌릴 수 있는 판단은 합리적으로 가정하고 `decision-log.md`에 기록한다.
4. 결제, 외부 전송, 운영 배포, 데이터 삭제, 계정·권한 변경처럼 외부에 되돌리기 어려운 작업은 명시적 승인 없이 실행하지 않는다.
5. 사용자의 기존 변경사항을 덮어쓰거나 관련 없는 파일을 되돌리지 않는다.
6. 테스트 통과만으로 완료라고 선언하지 않는다. 실제 실행 결과와 사용자 시나리오를 확인한다.
7. 오류가 없다는 이유만으로 품질이 좋다고 판단하지 않는다.
8. 주장마다 파일, 로그, 스크린샷, 테스트 결과, 재현 절차 중 하나 이상의 증거를 연결한다.
9. 규칙으로 판정할 사실과 AI가 해석할 판단을 분리한다.
10. Blocker 또는 Critical이 남아 있으면 종합 점수와 무관하게 PASS를 금지한다.
11. 완료 조건이 충족되지 않았는데 임의로 작업을 끝내지 않는다.
12. 동일 실패가 두 차례 연속 반복되고 새 증거나 개선이 없으면 무한 반복하지 말고 `BLOCKED`로 전환해 원인과 필요한 조치를 명시한다.

## 2. 프로젝트 발견과 기준 문서 확보

다음 순서로 조사한다.

1. `CLAUDE.md`, 중첩 `CLAUDE.md`, README, AGENTS.md, CONTRIBUTING, 기획서, 이슈, 설계 문서, 기존 품질 규칙을 읽는다.
2. 현재 브랜치, `git status`, 최근 변경 범위, 추적되지 않은 파일을 확인한다.
3. 진입점, 실행 명령, 빌드·테스트·린트·타입 검사, 배포 방식, 환경 변수, 외부 의존성을 찾는다.
4. `${CLAUDE_SKILL_DIR}/scripts/detect_project.py`를 실행할 수 있으면 사용한다. 실패하면 수동으로 동일 정보를 수집한다.
5. 프로젝트를 하나 이상의 유형으로 분류한다. 혼합 프로젝트는 관련 유형의 검수 항목을 합친다.
6. 사용자 유형, 핵심 사용자 여정, 실패 시 피해, 개인정보·금전·권한·외부 시스템 위험을 찾는다.
7. 최신성과 외부 사실이 중요한 내용은 이용 가능한 검색 도구와 공식 문서로 확인한다.

분류 규칙과 유형별 필수 검수는 [references/project-classification.md](references/project-classification.md)를 따른다.

## 3. 품질 작업공간과 SSoT

기존 품질 폴더가 없으면 `.claude/quality/`를 품질 SSoT로 사용한다.

```text
.claude/quality/
├── manifest.md
├── test-matrix.md
├── findings.jsonl
├── decision-log.md
├── final-report.md
├── project-detection.json
└── evidence/
    └── <run-id>/
```

`plan` 모드에서는 사용자 요청이 없는 한 계획 파일 외의 프로젝트 산출물을 수정하지 않는다. `audit` 모드에서는 소스 파일은 수정하지 않되 품질 보고서와 증거 파일은 작성할 수 있다.

필요하면 `${CLAUDE_SKILL_DIR}/scripts/bootstrap_quality.py --root .`로 기본 구조를 만든다. 기존 파일은 보존하고 누락된 파일만 생성한다.

## 4. 품질 매니페스트 작성

`manifest.md`에 다음을 명시한다.

- 프로젝트 목적과 이번 요청의 목표
- 대상 범위와 제외 범위
- 사용자·운영자·관리자·개발자 등 핵심 페르소나
- 핵심 사용자 여정과 성공 결과
- 프로젝트 유형과 기술 스택
- 실행·빌드·테스트 명령 및 필요한 환경
- 기능 요구사항과 비기능 요구사항
- 위험 요소와 우선순위
- 완료 정의(Definition of Done)
- 확인하지 못한 사항과 그 영향

요구사항마다 `REQ-*` ID를 부여하고 구현 파일·테스트·증거와 추적 가능하게 연결한다.

## 5. 베이스라인 확보

수정 전에 현재 상태를 기록한다.

- 빌드, 테스트, 린트, 타입 검사, 정적 분석 결과
- 애플리케이션 또는 산출물의 실제 실행·렌더링 결과
- 기존 오류, 경고, 실패 테스트, 깨진 링크, 콘솔·네트워크 오류
- 핵심 화면·출력·API·CLI 결과
- 실행 환경, 브라우저·기기·뷰포트, 테스트 데이터
- 변경 전 스크린샷·로그·DOM·응답·파일 해시 등 비교 가능한 증거

기존 실패와 이번 변경으로 생긴 실패를 구분한다. 베이스라인 실패를 숨기거나 성공으로 간주하지 않는다.

## 6. 검수 계획과 테스트 매트릭스

`test-matrix.md`에 다음 열을 사용한다.

```text
ID | 요구사항 | 사용자/환경 | 시나리오 | 검사 계층 | 예상 결과 | 증거 | 상태
```

모든 프로젝트에 공통으로 다음 계층을 검토한다.

1. 요구사항 완전성·추적성
2. 구조·정적 품질
3. 기능 정확성
4. 실제 런타임과 핵심 시나리오
5. 실패·경계·복구 시나리오
6. 보안·개인정보·권한·안전
7. 사용성·접근성·호환성
8. 성능·안정성·자원 사용
9. 관측 가능성·운영성
10. 문서·배포·롤백·인수인계

상세 검사 카탈로그는 [references/audit-matrix.md](references/audit-matrix.md)에서 관련 프로젝트 유형만 선택해 적용한다.

## 7. 실행과 구현

`full` 또는 `fix` 모드에서는 다음 순서로 작업한다.

1. 가장 작은 재현 사례로 문제를 확인한다.
2. 표면 증상이 아니라 근본 원인을 찾는다.
3. 변경 범위를 최소화하되 임시 우회가 아닌 지속 가능한 수정을 적용한다.
4. 요구사항·설계·코드·테스트·문서를 함께 동기화한다.
5. 수정 직후 대상 테스트를 실행한다.
6. 대상 테스트 통과 후 관련 회귀 테스트와 전체 게이트를 실행한다.
7. 작업 중 새 문제가 발견되면 findings에 추가하고 우선순위를 다시 계산한다.

관련 없는 리팩터링과 기능 확장은 별도 이슈로 분리한다. 사용자의 목표를 충족하기 위해 반드시 필요한 범위만 확장한다.

## 8. 실제 실행 기반 검증

실행 가능한 프로젝트를 코드만 읽고 검수하지 않는다.

- 앱·서버·CLI를 실제로 실행한다.
- 핵심 사용자 시나리오를 시작부터 성공 결과까지 수행한다.
- 각 중요 행동 전후에 상태와 증거를 수집한다.
- 성공 조건뿐 아니라 잘못된 입력, 권한 부족, 네트워크 실패, 빈 데이터, 중복 실행, 취소, 재시도, 복구를 확인한다.
- 테스트 더블만 통과한 상태와 실제 통합 환경 통과를 구분한다.
- 실행할 수 없는 경우 정확한 차단 원인과 누락된 검증 범위를 기록한다.

Claude Code의 `/run` 또는 `/verify`가 현재 프로젝트에서 사용 가능하고 프로젝트 실행 방식과 맞으면 활용한다. 그렇지 않으면 저장소의 실제 명령을 사용한다.

## 9. 웹 프로젝트 필수 Probe 파이프라인

브라우저 UI가 포함되면 각 핵심 상태와 사용자 행동마다 다음을 적용한다.

1. **DOM Probe**: 요소 존재, 구조, 속성, 상태, 중복 ID, 폼 연결
2. **Accessibility Probe**: 접근성 트리, role/name, 레이블, 제목 구조, ARIA, 대비
3. **Layout Probe**: 위치, 크기, 간격, 겹침, 잘림, 가로 스크롤
4. **Visibility·Occlusion·Hit-test Probe**: 실제 표시, 가림, 클릭 대상
5. **Visual Probe**: 실제 렌더링, 이미지·폰트·정렬·계층·빈 상태·오류 상태
6. **Responsive Probe**: 최소 모바일과 데스크톱, 위험도가 높으면 태블릿과 복수 브라우저
7. **Interaction Probe**: 클릭, 입력, 스크롤, 로딩, 중복 제출, 상태 전환
8. **Focus·Keyboard Probe**: Tab 순서, 포커스 표시, 모달 진입·복원, Escape
9. **Network Probe**: 4xx/5xx, 중복·느린·취소 요청, 계약 불일치
10. **Console Probe**: JS 예외, 미처리 Promise, hydration, CSP, 리소스 오류
11. **Storage Probe**: 쿠키, 세션, localStorage, 로그아웃·만료·사용자 격리
12. **Performance Probe**: 로딩, 상호작용, 레이아웃 이동, 긴 작업, 대용량 리소스
13. **Security Probe**: 인증·인가, 입력 검증, 비밀 노출, XSS·CSRF·오픈 리다이렉트 위험
14. **State Diff와 Post-action Verification**: 행동 전후 DOM·화면·URL·네트워크·저장 상태 비교

화면이 보인다는 사실과 클릭 가능하다는 사실을 구분한다. 클릭했다는 사실과 목표가 달성됐다는 사실도 구분한다.

## 10. 비웹 프로젝트 적용

웹이 아니면 관련 검수 모듈을 선택한다.

- API·백엔드: 계약, 인증·인가, 상태 코드, 데이터 무결성, 트랜잭션, 동시성, 멱등성, 마이그레이션, 관측성
- CLI·라이브러리: 입력·출력, 종료 코드, stdout/stderr, 도움말, 호환성, 취소·신호, 공개 API 회귀
- 모바일·데스크톱: 생명주기, 권한, 오프라인, 백그라운드, 상태 복원, 기기·OS 차이, 설치·업데이트
- 데이터·ML: 스키마, 누락·중복·이상치, 데이터 누수, 재현성, 평가셋, 편향, 드리프트, 모델·데이터 계보
- AI 에이전트·자동화·MCP: 도구 스키마, 권한 경계, 프롬프트 인젝션, 재시도, 멱등성, 중단·복구, 감사 로그, 비용 한도
- 인프라·DevOps: 구성 검증, 비밀, 최소 권한, 롤링·롤백, 상태·드리프트, 백업·복구, 장애 주입
- 문서·콘텐츠·디자인·미디어: 사실성, 출처, 구조, 일관성, 가독성, 접근성, 렌더링·내보내기 무결성, 해상도·비율·자산 누락

## 11. Findings 기록

발견한 문제는 한 줄 JSON 또는 동등한 구조로 `findings.jsonl`에 기록한다. 필수 필드는 다음과 같다.

```text
id, title, domain, severity, confidence, status,
requirement, environment, reproduction, expected, actual,
evidence, rootCause, remediation, verification, residualRisk
```

심각도·품질 게이트·완료 조건은 [references/quality-gates.md](references/quality-gates.md)를 따른다. 보고서 표현은 [references/reporting-schema.md](references/reporting-schema.md)를 따른다.

중복 증상은 공통 근본 원인이 확인된 경우 묶되, 영향을 받는 환경과 재현 경로는 모두 남긴다.

## 12. 수정·재검수 루프

다음 우선순위로 반복한다.

```text
Blocker → Critical → Major → Minor → Suggestion
```

각 이슈마다:

1. 재현
2. 원인 확인
3. 수정
4. 대상 검증
5. 관련 회귀 검증
6. 전체 핵심 시나리오 재검증
7. 증거 갱신
8. 잔여 위험 평가

새로운 Blocker·Critical이 생기면 이전 통과 판정을 취소한다. 같은 오류가 두 사이클 연속 동일하게 반복되면 환경·권한·설계·외부 의존성 문제인지 확인한 뒤 `BLOCKED`로 전환한다.

## 13. 독립 검수

최종 판정 전에 가능하면 깨끗한 컨텍스트의 별도 검수 에이전트를 사용한다.

독립 검수자에게는 목표, 요구사항, 변경 diff, 실제 산출물, 테스트 결과, 증거만 제공한다. 작성자의 변명·결론·자기평가는 제공하지 않는다. 검수자는 다음을 반박 관점으로 확인한다.

- 요구사항 누락
- 불필요한 과확장
- 숨겨진 가정
- 정상 경로만 검증한 문제
- 엣지케이스·회귀·호환성
- 보안·개인정보·안전 위험
- 테스트가 구현을 그대로 복제한 문제
- 증거가 결론을 지지하지 않는 문제
- 사용자 페르소나별 실패

프롬프트는 [references/independent-review.md](references/independent-review.md)를 사용한다. 독립 검수 결과는 `PASS`, `REVISE`, `BLOCK` 중 하나와 항목별 증거로 받아야 한다. 주 작업자는 반대 증거 없이 독립 검수 실패를 무시할 수 없다.

## 14. 최종 품질 게이트

다음 조건을 모두 확인한다.

- 목표와 요구사항이 산출물·테스트·증거로 추적된다.
- 미해결 Blocker와 Critical이 없다.
- 핵심 사용자 여정이 실제 실행 환경에서 성공한다.
- 실패·경계·복구 시나리오가 검증됐다.
- 빌드·테스트·정적 검사·런타임 검사가 적용 가능한 범위에서 통과한다.
- 보안·개인정보·접근성·성능·호환성 기준이 위험도에 맞게 검증됐다.
- 문서, 실행 방법, 설정, 마이그레이션, 롤백 정보가 현재 상태와 일치한다.
- 독립 검수가 PASS이거나, Critical 이하의 명시적 caveat만 남은 REVISE다.
- 확인하지 못한 영역과 잔여 위험이 숨김없이 기록됐다.

최종 판정은 네 가지 중 하나만 사용한다.

- `GO`: 완료 조건 충족
- `GO_WITH_CAVEATS`: Blocker·Critical은 없지만 수용 가능한 잔여 위험 존재
- `NO_GO`: 해결 가능한 중대 결함이 남음
- `BLOCKED`: 권한·환경·외부 의존성 때문에 필수 검증 또는 수정이 불가능

점수는 보조 지표일 뿐 게이트를 대체하지 않는다.

## 15. 최종 산출물과 응답

`final-report.md`에 다음 순서로 작성한다.

1. 최종 판정
2. 수행한 범위와 제외 범위
3. 프로젝트 유형과 적용한 검수 모듈
4. 요구사항별 통과 현황
5. 수정 사항
6. 실행한 테스트와 실제 시나리오
7. 미해결 이슈와 잔여 위험
8. 증거 파일 위치
9. 재현·실행·롤백 방법
10. 다음 승인 또는 배포 전에 필요한 조치

사용자에게는 장황한 작업 로그 대신 다음을 명확히 알린다.

- 무엇을 실제로 확인하고 수정했는가
- 최종 판정은 무엇인가
- 어떤 증거가 있는가
- 무엇이 남았는가
- 남은 문제를 해결하려면 무엇이 필요한가

완료되지 않은 작업을 완료됐다고 표현하지 않는다.
