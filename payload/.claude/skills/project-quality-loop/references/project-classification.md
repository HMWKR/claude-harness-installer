# 프로젝트 분류 및 적용 규칙

이 문서는 현재 프로젝트를 하나 이상의 유형으로 분류하고, 어떤 품질 검수 모듈을 반드시 적용할지 결정하는 기준이다.

## 1. 분류 원칙

1. 프로젝트를 억지로 하나의 유형에만 넣지 않는다.
2. 사용자에게 전달되는 최종 산출물과 실제 실행 경로를 기준으로 분류한다.
3. 저장소의 파일 확장자보다 런타임, 데이터 흐름, 사용자 행동, 운영 위험을 우선한다.
4. 혼합 프로젝트는 관련 유형의 필수 검사를 합친다.
5. 금전, 인증, 개인정보, 권한, 의료·법률·재무, 외부 전송, 운영 인프라가 포함되면 위험 등급을 한 단계 올린다.

## 3. 위험 신호

다음 항목이 있으면 일반적인 기능 검수만으로 충분하지 않다.

### Blocker급 위험 후보

- 결제, 주문, 정산, 송금
- 인증, 권한, 관리자 기능
- 개인정보, 위치, 건강, 금융 데이터
- 데이터 삭제, 대량 변경, 복구 불가능 작업
- 운영 배포, DNS, 인증서, 인프라 변경
- 외부 메시지·이메일·게시·파일 전송
- 안전과 직접 관련된 자동화

### 고위험 검수 강화

- 최소 2개의 독립 검증 경로를 사용한다.
- 정상 경로 외에 권한 부족, 재시도, 중복 요청, 타임아웃, 부분 실패를 검증한다.
- 테스트 데이터와 운영 데이터를 엄격히 구분한다.
- 로그와 증거에서 비밀·개인정보를 마스킹한다.
- 외부 side effect는 승인 게이트를 둔다.
- 실패 시 롤백·보상 트랜잭션·재처리 방식을 확인한다.

## 4. 페르소나 추출

프로젝트 문서에 명시되지 않았으면 다음 순서로 추론한다.

1. 직접 사용자: 기능을 사용하는 사람
2. 운영자: 콘텐츠·데이터·정책을 관리하는 사람
3. 관리자: 권한·설정·감사를 담당하는 사람
4. 개발자·통합자: API, SDK, CLI를 사용하는 사람
5. 지원 담당자: 장애를 재현하고 설명해야 하는 사람
6. 공격자·오용자: 권한을 우회하거나 입력을 악용하려는 사람
7. 접근성 사용자: 키보드, 스크린리더, 확대, 저시력 환경 사용자

각 핵심 시나리오에는 최소 한 명의 페르소나를 연결한다.

## 5. 핵심 사용자 여정 선정

다음 기준으로 P0/P1/P2를 나눈다.

- P0: 실패하면 프로젝트의 핵심 가치가 사라지거나 금전·데이터·권한 피해가 발생
- P1: 핵심 업무의 일부가 불가능하거나 큰 우회가 필요
- P2: 사용은 가능하지만 품질·효율·이해에 문제가 있음

최소 구성:

- P0 정상 경로
- P0 실패 경로
- 인증·권한 경계
- 데이터 없음·빈 상태
- 네트워크·외부 의존성 실패
- 중복 실행·재시도
- 취소·뒤로가기·중단 후 복구
- 모바일 또는 작은 화면, 해당 시

## 6. 혼합 프로젝트 규칙

예: Next.js + API + PostgreSQL + Kubernetes 프로젝트

```text
Web UI 검수
+ Backend/API 검수
+ Database 검수
+ Infrastructure 검수
+ 브라우저→API→DB까지의 실제 E2E
+ 인증·권한·데이터 경계 검수
```

구성요소별 테스트가 모두 통과해도 종단 간 시나리오가 실패하면 최종 판정은 실패다.
