# 심각도, 완료 조건, 품질 게이트

## 1. 심각도

### Blocker

핵심 목표를 완료할 수 없거나 즉각적인 중대 피해가 발생할 수 있다.

- 앱·서비스가 실행되지 않음
- 로그인·결제·저장·핵심 작업 불가
- 데이터 손실·오염·권한 우회
- 비밀·개인정보 노출
- 배포·마이그레이션이 복구 불가능한 상태를 만듦
- 필수 산출물을 열거나 제출할 수 없음

### Critical

많은 사용자 또는 중요한 사용자 집단이 핵심 기능을 사용할 수 없고, 안전한 우회가 어렵다.

- 모바일 또는 특정 브라우저에서 핵심 CTA가 가려짐
- 객체 수준 권한 오류
- 중복 주문·중복 처리 위험
- 실패 시 상태가 복구되지 않음
- 주요 문서의 핵심 수치나 결론이 잘못됨

### Major

작업은 가능하지만 큰 오류, 혼란, 성능 저하, 운영 부담이 있다.

- 주요 폼 검증·오류 메시지 문제
- 비핵심 시나리오 실패
- 반복적인 API 중복 호출
- 접근성 사용자가 중요한 일부 기능을 사용하기 어려움
- 문서의 중요한 누락·모순

### Minor

기능에는 큰 영향이 없지만 품질과 일관성을 저해한다.

- 간격·정렬·표기 불일치
- 경미한 경고
- 낮은 우선순위 문서 누락
- 드문 조건의 비핵심 불편

### Suggestion

현재 요구사항을 위반하지 않지만 향후 가치가 있는 개선 제안이다. 미구현을 실패로 계산하지 않는다.

## 2. 확신도

- `HIGH`: 직접 재현했고 증거가 명확함
- `MEDIUM`: 여러 정황이 일치하지만 완전한 재현 또는 원인 확인이 부족함
- `LOW`: 가설 또는 잠재 위험. 실패로 단정하지 않고 추가 확인 필요

LOW 확신도 이슈를 Blocker 또는 Critical로 단정하려면 추가 증거를 확보해야 한다. 다만 보안·데이터 손실처럼 피해가 큰 경우 보수적으로 `BLOCKED_PENDING_VERIFICATION` 상태를 사용할 수 있다.

## 3. 상태

- `OPEN`: 확인된 미해결 문제
- `IN_PROGRESS`: 수정 중
- `FIXED_UNVERIFIED`: 수정했지만 재검증 전
- `VERIFIED`: 동일 조건에서 해결 확인
- `REGRESSION`: 수정으로 새 문제 발생
- `ACCEPTED_RISK`: 명시적으로 수용된 잔여 위험
- `NOT_REPRODUCED`: 현재 조건에서 재현 실패
- `BLOCKED`: 환경·권한·외부 의존성으로 진행 불가
- `DUPLICATE`: 다른 근본 이슈에 병합

`FIXED_UNVERIFIED`는 완료가 아니다.

## 4. Definition of Done 기본값

다음은 프로젝트 특성에 맞게 조정하되 이유 없이 삭제하지 않는다.

1. 사용자 목표가 명확한 요구사항으로 정리됐다.
2. 각 요구사항이 구현·테스트·증거에 연결됐다.
3. 핵심 사용자 여정이 실제 실행 환경에서 성공했다.
4. 실패·경계·복구 시나리오를 검증했다.
5. 적용 가능한 빌드·테스트·정적 검사가 통과했다.
6. 적용 가능한 런타임·통합·E2E 검사가 통과했다.
7. 미해결 Blocker·Critical이 없다.
8. Major는 수정됐거나 명시적 수용 근거가 있다.
9. 보안·개인정보·권한·안전 위험을 점검했다.
10. 접근성·호환성·성능 기준을 위험도에 맞게 확인했다.
11. 문서, 설정, 예제, 마이그레이션, 롤백 정보가 현재 상태와 일치한다.
12. 독립 검수가 증거 기반으로 결론을 확인했다.
13. 확인하지 못한 영역과 잔여 불확실성을 공개했다.

## 5. 최종 판정

### GO

- 모든 필수 DoD 충족
- Blocker·Critical 0건
- 미해결 Major는 없거나 실제 영향이 없는 것으로 증명
- 핵심 여정과 회귀 검증 통과
- 독립 검수 PASS

### GO_WITH_CAVEATS

- Blocker·Critical 0건
- 핵심 여정 통과
- 배포·전달을 막지 않는 Major/Minor 또는 NOT_RUN 항목이 존재
- 잔여 위험, 영향 대상, 완화책, 후속 기한이 명시됨
- 사용자가 위험을 이해할 수 있을 정도의 증거가 있음

### NO_GO

- 해결 가능한 Blocker 또는 Critical이 남음
- 핵심 여정 실패
- 데이터·권한·금전·안전 위험을 통제하지 못함
- 수정 후 회귀가 발생
- 문서나 산출물이 제출·실행 불가능

### BLOCKED

- 필수 환경, 자격증명, 권한, 데이터, 기기, 외부 서비스가 없어 검증 불가
- 외부 시스템 장애로 결과를 확인할 수 없음
- 승인 없이는 실행할 수 없는 고위험 side effect가 필수임
- 두 차례 연속 같은 실패가 반복되고 새 증거 또는 진전이 없음

BLOCKED는 실패를 숨기는 판정이 아니다. 다음을 반드시 포함한다.

- 막힌 정확한 단계
- 시도한 내용
- 수집된 증거
- 필요한 권한·환경·결정
- 해제 후 가장 먼저 실행할 검증

## 6. 게이트 순서

```text
Gate 0: 범위·요구사항 게이트
Gate 1: 정적 품질 게이트
Gate 2: 기능·런타임 게이트
Gate 3: 실패·복구 게이트
Gate 4: 보안·개인정보·권한 게이트
Gate 5: 사용성·접근성·호환성 게이트
Gate 6: 성능·안정성·운영 게이트
Gate 7: 문서·릴리스·롤백 게이트
Gate 8: 독립 검수 게이트
```

앞 단계의 Blocker를 무시한 채 뒤 단계 점수로 상쇄하지 않는다.

## 7. 반복 개선 규칙

1. Blocker부터 수정한다.
2. 한 사이클에서 관련 없는 대규모 변경을 섞지 않는다.
3. 수정 전 재현 증거를 확보한다.
4. 수정 후 대상 검증과 전체 핵심 회귀를 분리해 실행한다.
5. 같은 실패가 반복되면 단순 재시도 대신 가설을 바꾼다.
6. 두 차례 연속 결과가 같고 새 정보가 없으면 `BLOCKED`로 전환한다.
7. 새 Blocker·Critical이 생기면 이전 GO 후보를 취소한다.
8. 테스트를 삭제하거나 기준을 낮춰 통과시키지 않는다. 기준 변경이 필요하면 근거를 decision log에 기록한다.

## 8. 점수 사용 규칙

점수가 필요하면 영역별로 분리한다.

```yaml
functional: 0-100
security_privacy: 0-100
accessibility_usability: 0-100
performance_reliability: 0-100
maintainability: 0-100
documentation_operations: 0-100
```

다음은 금지한다.

- Blocker가 있는데 평균점수로 GO 처리
- 실행하지 않은 검사를 0이 아닌 통과 점수로 처리
- 가중치만 바꿔 실패를 숨김
- AI의 주관적 인상만으로 수치 생성

## 9. 승인 게이트

다음은 명시적 승인 전 실행하지 않는다.

- 운영 배포
- 실제 결제·주문·송금
- 실제 이메일·메시지·게시
- 실제 고객·개인정보 데이터 변경
- 대량 삭제·마이그레이션·권한 변경
- DNS, 인증서, 운영 인프라 변경
- 비용이 큰 외부 작업

승인 전에는 dry run, preview, staging, mock, plan, diff, 영향 분석까지 수행한다.
